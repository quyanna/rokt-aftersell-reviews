# Shopify review → support triage sheet

Reads the public Shopify App Store reviews for **Aftersell** (post-purchase upsells)
and **UpCart** (cart drawer), then works out what a support person would actually
have to do about each recurring complaint.

Not market research. The question throughout is *what would land in my ticket queue,
and what would stop it landing there.*

Point it at any Shopify app slug and it works.

## The honest caveat, up front

**People who quietly uninstall an app never write a review.** This dataset measures
*loud* complaints, not *common* ones. Real ticket volume would skew far more mundane —
password resets, "where is this setting", billing questions that never reach a public
review page. Every number here should be read as "of the people angry enough to post
in public", never as "of merchants".

There are also only ~90 negative reviews across both apps. That is enough to describe
patterns. It is not enough for statistics, and nothing in this project claims
otherwise.

## How to run it

Requires [uv](https://docs.astral.sh/uv/) (a Python runner that installs its own
dependencies). Nothing else to install — no virtualenv, no `pip install`.

```bash
uv run fetch.py
```

That is stage 1. Later stages are added as they are built.

## The five stages

| Stage | Script | What it does | Status |
|---|---|---|---|
| 1 | `fetch.py` | Download every review page, save the raw HTML | Done |
| 2 | `parse.py` | Pull the reviews out of the HTML into a SQLite database | Not started |
| 3 | `classify.py` | Have Claude categorise each review, then hand-check its work | Not started |
| 4 | `docs_match.py` | Check each complaint against Aftersell's own help docs | Not started |
| 5 | `report.py` | Build the triage sheet as a single HTML page | Not started |

Each stage is a separate script on purpose. Parsing HTML is fiddly and the parser will
have bugs; keeping the download separate means those bugs get fixed against files
already on disk rather than by hammering Shopify's servers again.

**Every stage is re-runnable and picks up where it left off.** Nothing re-downloads or
re-classifies work already done. Re-running the whole pipeline should cost nothing.

## Stage 1: what was collected

| App | Pages | Reviews |
|---|---|---|
| `aftersell` | 91 | 905 |
| `upcart-cart-builder` | 86 | 860 |

~43MB of raw HTML in `data/raw/`, one file per page.

**The raw HTML is not in this repository.** It is regenerated by running `fetch.py`,
which takes about three minutes. Committing 43MB of machine-generated markup that
nobody will ever read would make the repo slow to clone for no benefit.

### Was scraping this OK?

Checked before writing any code:

- `apps.shopify.com/robots.txt` explicitly **allows** `/reviews`. The disallowed paths
  are `/internal/`, `/services/`, search queries and authentication parameters.
- No crawl-delay directive is set. The script waits **one second between requests**
  anyway, which is slower than a person clicking through pages.
- The script sends a **User-Agent that identifies itself** and includes a contact
  email, so Shopify can get in touch rather than having to guess who is doing this.
- All of this data is **public** — anyone can read it in a browser without logging in.

~180 requests, one per second, once. Re-runs make zero requests.

## Working with AI on this project

Claude is used in two distinct ways here, and the difference matters:

1. **Writing the code.** Every line was read and understood before running. Where the
   generated code was wrong, it was corrected — those corrections are logged in
   [NOTES.md](NOTES.md).
2. **Classifying the reviews** (stage 3). This is the part where blindly trusting the
   output would be a real mistake, so stage 3 includes a **hand-audit**: a random
   sample of reviews gets labelled by hand, without looking at the model's answer, and
   the two are compared. The agreement rate and every disagreement are published in
   `NOTES.md` and in the final report.

An analysis that says "I asked an AI and here are the results" is worth less than one
that says "here is where I checked it, and here is where it was wrong."

## No secrets in this repo

The Anthropic API key needed for stage 3 is read from the `ANTHROPIC_API_KEY`
environment variable. It is never written to a file in this project. `.gitignore`
covers `data/` and `.env` and was committed *before* any data existed — deleting a
file from git later does not remove it from the history.
